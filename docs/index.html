Forward path and return path

Forward: App-A (10.10.2.10) sends to 10.20.1.10. Its route table matches 10.20.0.0/16 and sends the packet into the peering connection to VPC B.

Return: App-B replies to 10.10.2.10. Its route table matches 10.10.0.0/16 and sends the reply back through the peering connection. Without this return route the reply is lost.

Public route: the bastion opens the SSH connection to App-B, so the public subnet also needs 10.20.0.0/16 → peering. The more specific /16 wins over 0.0.0.0/0.

Viva answers

1. Why is the return route needed?

A reply must travel back too. If only one side has a route, the request arrives but the answer cannot find its way home.

2. Why is the App-B SSH source the bastion’s private IP?

The bastion opens a separate SSH connection to App-B from inside the network, so App-B sees the bastion’s private address, not my laptop.

3. Why does Active peering not guarantee a successful ping?

Peering is only the link. Route tables must point to it on both sides and security groups must allow the traffic.

4. Can VPC B use VPC A’s internet gateway over peering?

No. Peering does not pass internet access through to the other VPC.
